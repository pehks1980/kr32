KR32 kernel memory map
=====================

This document describes the layout defined by kernelshed.asm and the generated
TAR image. Addresses are hexadecimal. Pages are 0x1000 bytes. Ranges below are
inclusive unless marked as exclusive or described as an end symbol.

Kernel image and bootstrap
-------------------------

The kernel entry is at 0x00002000. Each task page table identity-maps
0x00000000-0x00014FFF for kernel code and static data. BMI buffers/registers
are mapped separately at 0x00015000-0x00017FFF.

KERNEL_START sets the bootstrap SP to 0x0003E000 before making calls or pushing
registers. This temporary stack grows through 0x0003D000-0x0003DFFF and is used
before the MMU is enabled. It is not a task's kernel stack, and this range is
not part of the common post-bootstrap mappings. KERNEL_BASE (0x00000000) and
KERNEL_LIMIT (0x0003DFFF) are address-validation bounds, not a declaration that
the whole range is mapped.

Common kernel mappings
----------------------

map_common_kernel installs these identity mappings in every task page table.
They use supervisor-only kernel permissions:

  0x00000000-0x00014FFF  Kernel code and static data
  0x00015000-0x00017FFF  BMI buffers and registers
  0x00050000-0x000CFFFF  Physical page allocator pool
  0x000D0000-0x000EAFFF  Built-in TAR image mapping
  0x00100000-0x00102FFF  UART, PIT, and PIC MMIO pages

The TAR image bytes occupy 0x000D0000-0x000EB5FF; tarfs_end is the exclusive
end address 0x000EB600. The mapping loop rounds up to a page boundary, so the
last mapped page is 0x000EA000-0x000EAFFF. The image is outside the allocator
pool.

Per-task address spaces
-----------------------

The user-pointer bounds are USER_BASE = 0x0003E000 through USER_LIMIT =
0x0005FFFF, inclusive. Validation also checks that every page touched by a
pointer is present and user-accessible in the current task's page table. The
bounds alone do not make an address mapped.

Current user virtual addresses and mappings:

  0x0003F000  User stack page; initial user SP is 0x00040000
  0x00040000  Initial task code page; TASK_INIT_START is in this page
  0x00042000  Per-task user data and heap page
  0x00043000  Starting VA for an execve-loaded program image

Task creation allocates a distinct physical user-stack page and data page for
each task, mapping them read/write for user mode at 0x0003F000 and 0x00042000.
The heap occupies 0x00042100-0x00042FFF; its initial break is 0x00042100.
The task's entry-code page is mapped from the entry address. execve maps its
loaded image starting at 0x00043000. These mappings are task-specific.

Each task also receives a dynamically allocated physical kernel-stack page.
The initial trapframe is built on that page. Kernel stacks, page tables, file
descriptor tables, kernel buffers, and user pages are allocated from the
physical page pool and accessed through the common supervisor mapping.

Physical page allocator
-----------------------

The active allocator manages 128 pages of 0x1000 bytes each:

  Base:             0x00050000
  End (exclusive):  0x000D0000
  Capacity:         0x00080000 bytes (512 KiB)

page_alloc uses the 128-byte page_refcounts array to find free pages; the
array is cleared during page-table initialization. The source also retains
older bitmap-based routines and data, but they are not the active allocator.
The TAR image begins at the pool's exclusive end, so it does not overlap these
allocations.

Bootstrap sequence
------------------

1. Enter KERNEL_START and set SP to 0x0003E000 before any push.
2. Initialize page-allocation state, then create task page tables and their
   kernel stacks, trapframes, user stacks, data pages, and mappings.
3. Mount the built-in TAR image and select the initial task's PTBR and KSP.
4. Enable the MMU and restore the selected task's trapframe.
